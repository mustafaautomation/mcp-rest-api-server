The boring parts, already done.

The interesting work is mapping your API. The server around it — validation, paging, auth, and the client config — should not be a weekend of glue.

Read-only until you say otherwise

Write tools are not registered while MCP_READ_ONLY is true. The HTTP client also refuses POST and PATCH, so a new tool cannot slip past the flag.

Cursors, not page numbers

Tools take limit and cursor and return nextCursor. If your API uses page numbers, the adapter lives in the client, not in the prompt.

Keys stay out of the log

Bearer or x-api-key, from the environment. Tool errors and stderr are scrubbed. A reflected key comes back as [redacted].

Retries that respect writes

Reads back off on 429 and 5xx and honor Retry-After. Writes retry a rate limit. They do not retry a 500.

Resources and prompts

A project snapshot, a contract resource, and two prompts that load live tasks before they ask the model to write.

Tests against a real socket

Vitest boots the sandbox and drives the server with the official MCP client, over an in-memory pair, Streamable HTTP, and stdio.

Where a call goes.

One process. The model never sees the API key. Harborline stands in until you set API_BASE_URL.

A live endpoint, still read-only.

After deploy, clients connect to https://mcp-api.quvantic.com/mcp. One POST, JSON in and JSON out, Harborline data only. The function stays inside the Hobby time limit. It will not call your API and it will not write.

Paste a config.

Stdio is the path all three clients launch. Swap the base URL and use a read-only key. Local checkouts can point command at node dist/cli.js before the package is on npm.

{
  "mcpServers": {
    "harborline": {
      "command": "npx",
      "args": ["-y", "mcp-rest-api-server"],
      "env": {
        "API_BASE_URL": "https://api.example.com",
        "API_KEY": "YOUR_API_KEY",
        "MCP_READ_ONLY": "true"
      }
    }
  }
}
